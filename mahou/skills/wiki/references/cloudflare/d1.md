# D1: SQLite on Cloudflare, migrations and drivers

verified: 2026-10-04

Answers what D1 offers as a database, how it is reached, how its schema is migrated, and whether SQLAlchemy and Alembic can drive it. Distilled from documentation and package inspection while weighing a Postgres-to-D1 move; nothing was run against D1.

## Knowledge

- D1 runs on SQLite's engine with the JSON extension, FTS5 and math functions. `PRAGMA foreign_keys` and `defer_foreign_keys` are available. `run()` returns `meta.changes`, so a conditional `UPDATE ... WHERE status = ...` can be checked by its row count. `batch()` runs its statements as one transaction.
- Limits on Paid: 10 GB per database (500 MB on Free), 2 MB per row or value, 100 bound parameters per query, 1,000 queries per Worker invocation. Each database is single-threaded.
- Pricing on Paid includes 25 billion rows read, 50 million rows written and 5 GB a month; beyond that $0.001 per million reads, $1.00 per million writes and $0.75 per GB-month. No egress charges.
- From a Worker it is a binding. From anything else, such as a container, the only documented route is the REST API.
- Migrations are hand-written `.sql` files in a `migrations/` folder, created with `wrangler d1 migrations create`, applied with `--local` or `--remote`, and tracked in a `d1_migrations` table. There is no down migration: a failing migration rolls back itself and the earlier ones stay. Time Travel keeps 30 days of point-in-time restore on Paid (7 on Free).
- Read replication is GA at no cost; without the Sessions API every query goes to the primary, and with it reads are sequentially consistent.
- `sqlalchemy-cloudflare-d1` (0.4.1, 2026-10-02) connects over the REST API or a Python Worker binding. Its async engine is unavailable inside Workers, its `commit` and `rollback` are no-ops because every statement auto-commits, and its package contains no Alembic support. No other package connects Alembic to D1; Alembic's offline `--sql` output written into D1's migration files is an untested route.
