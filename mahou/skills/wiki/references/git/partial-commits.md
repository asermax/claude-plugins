# Committing only your hunks from a shared checkout

verified: 2026-11-23

How to commit some hunks of some files when other people edit the same checkout at the same time, have entries staged in its index, and have their own uncommitted hunks in files you also changed.

## Knowledge

- `git commit` with no paths commits everything staged, including entries someone else staged. `git commit -- <paths>` (the default `--only` mode) commits the whole working-tree content of those paths, including other people's hunks in them. Neither commits only your hunks.
- Commit from a temporary index instead: `GIT_INDEX_FILE=<tmp> git read-tree HEAD`, then `GIT_INDEX_FILE=<tmp> git apply --cached mine.patch`, then `GIT_INDEX_FILE=<tmp> git commit -F msg`. The commit holds HEAD plus your patch and nothing else; other people's staged entries stay staged in the real index. Commit hooks still run, and they run against the working tree, so they can fail on someone else's unfinished files; wait and retry instead of bypassing the hook.
- lefthook hides the unstaged hunks of a partially staged file while its pre-commit hook runs, so the hook checks your staged half of that file against everyone else's working-tree content in the other files. When the unstaged hunk you left out is someone else's rename that their other, unstaged files already use (a field `archived` renamed `isArchived` across the tree), the typecheck fails on your file with the old name, though the full working tree typechecks. Wait until they commit the rename; then the whole diff of that file is yours, and you stage it in full.
- Give each commit a fresh temporary index path (a timestamp in the name) instead of `rm -f "$tmp"` before `read-tree`. Claude Code's safety check refuses a removal whose target it cannot resolve, such as a path held in a shell variable, and a permission prompt nobody answers times out, so the whole command, commit included, does not run.
- Run `read-tree` through `commit` in one critical section (inside the same lock the other agents commit under). A commit that lands between `read-tree` and `commit` is otherwise dropped from your commit's tree.
- Build `mine.patch` from `git diff -- <file>` and drop the hunks that are not yours by their changed lines (those starting with `+` or `-`). Context lines can contain the word you filter on (`TransactionModel` contains `Mode`), so filtering whole hunks by text drops your own. A new file you created goes in with `git diff --no-index -- /dev/null <path>`. Make each diff end with a newline before concatenating them; a runner that trims output joins the last line of one diff to the `diff --git` header of the next, and `git apply` reports "patch does not apply".
- When a file's committed version must differ from both HEAD and the working tree (only some of your hunks in this commit), write the content you want, hash it with `git hash-object -w <file>` and stage it with `GIT_INDEX_FILE=<tmp> git update-index --cacheinfo 100644,<blob>,<path>`. Keep the file's final newline: a runner that trims command output drops it when the content comes from `git show HEAD:<path>`, and a formatter check in the hook then rejects the file.
- Check the patch first against a throwaway index: `GIT_INDEX_FILE=<tmp2> git read-tree HEAD && GIT_INDEX_FILE=<tmp2> git apply --cached --check mine.patch`.
- After the commit, the real index still holds the old blobs of the paths you committed, so `git status` shows them as staged reverts (`MM`, or `D` plus `??` for a file you created). `git reset -q -- <your paths>` resets only those index entries to the new HEAD and leaves the working tree, including other people's hunks, untouched.
- When someone else's unfinished files keep failing a hook that checks the whole working tree, commit from a worktree that holds only your changes, so the hook checks exactly what you commit, still without bypassing it: `git worktree add --detach <dir> "$base"` with `base=$(git rev-parse HEAD)`, copy your files in, install the dependencies the hook needs there, and commit. Then move the branch with `git update-ref refs/heads/<branch> <new commit> "$base"`, which refuses when someone committed in the meantime, reset your paths in the real index as below, and `git worktree remove` the directory. The shared checkout's working tree already holds your content, so your paths show as clean afterwards.
- When `update-ref` refuses because someone committed to the branch while you worked in the worktree, rebase the worktree's commits onto the new tip (`git -C <dir> rebase --onto <new tip> "$base"`), run the hook's check in the worktree again, since a rebase runs no pre-commit hook, then `update-ref` with the new tip as the old value. Their commit holds their files, so check first that it touches none of yours (`git diff --name-only "$base" <new tip>`).
- Install the worktree's dependencies with `pnpm install --frozen-lockfile --offline --ignore-scripts` to skip the `prepare` script and leave the shared hooks alone; a hook that runs typecheck, lint, tests and format still passed in such a worktree.
- Installing the dependencies in that worktree runs the project's `prepare` script, and a hook manager installed from it (lefthook, husky) rewrites the hook scripts in the shared `.git/hooks`, which every worktree of the repository uses. lefthook writes the absolute path of the worktree's own binary into them, so after `git worktree remove` the shared checkout's hook points at a binary that is gone and survives only through its fallbacks. After removing the worktree, run the hook manager's install again from the shared checkout (`pnpm exec lefthook install`) and check the path in `.git/hooks/pre-commit`.
- A fresh worktree has the installed dependencies but none of the build output its workspace packages export (a `dist/` behind a subpath export such as `@scope/core/contracts`). Running the test runner directly there fails every suite that imports one with "Cannot find package". Run the tests through the monorepo's task runner (`turbo run test --filter <app>`), whose `test` task depends on the packages' `build`, so it builds them first.
- A script that makes two commits under `set -e` can stop after the first commit landed, when the second one's hook fails. Read `git log` before rerunning it: applying the first patch again against a HEAD that already has it fails with "already exists in index" and "patch does not apply".

The worktree had been installed with `--ignore-scripts`, and the shared `.git/hooks/pre-commit` kept its checkout's lefthook path.
