# Releasing a Dialog whose model is dropped with its view

verified: 2026-11-23

Why a `@foldkit/ui` `Dialog` stops answering Escape after its parent drops the model while it is open (for example a sheet held in an `Option` that becomes `None` on close), and how to release what it holds.

## Knowledge

- `Dom.showDialog` (run by the `ShowDialog` command and by the `AcquireResources` Mount) calls `element.show()`, not `showModal()`. Escape is not the native dialog's: a `keydown` listener on `document` dispatches a `CustomEvent('cancel')` on the topmost dialog of Foldkit's own stack, and the view maps it to `RequestedClose`. The listener, the stack entry, the focus trap, the return focus, the background isolation and one scroll lock are stored per dialog id in a module-level map.
- `showDialog` returns early, without calling `show()` or adding a listener, when that map already holds an entry for the id.
- The entry is removed by `closeDialog` (the `CloseDialog` command, issued by `RequestedClose`), by `releaseDialogResources` (the `ReleaseDialogResources` command, issued when the view's `OnUnmount` sends `Unmounted` to an open model), or by the `AcquireResources` Mount's finalizer, but only when that Mount was the one that acquired. When `ShowDialog` acquires first, the Mount gets `false` and releases nothing on unmount.
- A parent that drops the Dialog model in the same update that closes the view (`sheet: Option.none()`) sends no `RequestedClose`, and the `Unmounted` message reaches a parent that no longer holds the child, so it is ignored. The entry leaks. The next dialog with the same id is never shown: it gets no listener, and Escape dispatches `cancel` on the detached element of the earlier opening, so nothing happens. The click handlers on the backdrop and the close button still work, because they are view event handlers. The leak also keeps one scroll lock and the stale stack entry.
- Foldkit's `Unmounted` does fire for a dropped dialog: the view puts `OnUnmount(Unmounted())` on the `<dialog>` while it is visible, and snabbdom's destroy hook runs for every element of a removed subtree. `OnUnmount` resolves the Submodel wrapping chain when the element renders, so the message reaches the root update wrapped in every `Got*Message` even after the screen or sheet that owned the dialog is gone. Patch-time dispatches are buffered and processed right after the patch. Two things stop it from releasing anything: `Unmounted` has no fields, so it does not carry the id, and every parent's fold drops it because `read` returns `None`.
- Fix: whenever an open Dialog element leaves the page without a close, issue `Dialog.ReleaseDialogResources({ id })` (Foldkit's documented cleanup for "the element is removed without a close Message"). To do this without a list of dialogs, have each shared dialog host add a second `OnUnmount` to the `<dialog>` while `render.isVisible`, carrying an app message with the id, such as `UnmountedDialog({ dialogId })`. `attachOnUnmount` keeps every `OnUnmount` on one element, so Foldkit's own `Unmounted` still reaches a kept model. The `toView` slot runs in the owner's boundary, so the message must belong to the owner's Message union. Each owner union needs the variant, and its update treats it as a no-op. The root update then searches the incoming message for that variant by following nested `message` fields, and issues the release. This covers close, save, browser Back, a route change, a lost session, and nested pickers and confirm dialogs. Map the command's result through a `Got*Message` wrapper, because `foldkit(wrap-child-output-in-got-message)` rejects a plain `Completed*` mapper.
- The older approach compares a hand-written list of every Dialog model on the screen before and after each message and releases each id that was open before and is absent after. The list goes stale when a dialog is added, as Settings' currency picker showed.
- Releasing from the unmount does not race a same-id reopen in practice: when the model is replaced and reopened under the same id in one update, the element is patched in place, so no unmount fires. A reopen under the same id on a *new* element in the same patch would still break, with either approach: `ShowDialog` runs in a microtask before the render and returns early on the leaked entry, and a later release would strip the new element's resources.
- A Dialog model the parent keeps (closed through `Dialog.close`) never leaks: `CloseDialog` releases the entry even when the element is already gone, because it falls back to `releaseDialogResources`.
- The node scene and story runners do not run `Dom` and never fire `OnUnmount`, so a test cannot reproduce the dead Escape. A story test can send the wrapped unmount message to the root update after the model is dropped, and check that the release command is issued. A browser check that patches `HTMLDialogElement.prototype.show` and `close` and `EventTarget.prototype.dispatchEvent` for `cancel` events shows the leak: the second opening logs no `show`, and Escape logs `cancel` on a target whose `isConnected` is false.
