# Mahou

Mahou (魔法) is magic. The agent is the magic: tireless, fast, and exactly as wise as the instructions it is given. You are the spellcaster. You draw the circle, you provide the mana, you choose the spell, and the agent pours itself into the shape you drew.

No spell casts itself. No skill picks a library for you, no skill chooses between two designs, no skill guesses what you meant. Every decision stays with you, and the skills are built to keep it that way.

## Philosophy

Four commitments, mirrored in `mahou:basics`:

- You decide, the agent executes. Skills bring facts and state; decisions stay with you.
- One skill, one job. Skills stay small. A skill that needs a second job becomes two skills.
- Process lives in skills, knowledge lives in the wiki, and the project's own documentation lives in the project. A skill is how to work; a fact about a technology is a wiki entry; how this system works is a note in the project's `docs/`.
- Nothing is committed unprompted.

## How to use it

Not sure which skill fits? Describe the goal in plain words to `mahou:guide` and it routes you to the right skill. Know the skill you want? Name it directly.

A piece of work usually runs through the skills in this order: `explore` to build the understanding, `shape` to settle the decisions, `design` and `program-design` to settle the system and the program, `test-design` to settle what proves it, `implement` to get it written (or you write it yourself), `validate` to see it working, `agentic-review` to clean it up, then `code-blast-radius` and `human-review` look at it, `write-documentation` records what got built, and `commit-changes` lands it. When the change spans repositories, `release-check` says what breaks in which deploy order and `land` takes it through the merges in the safe order. Each stage is its own skill and you start each one yourself.

## Skills

Process, in the order work moves through them:

- `mahou:explore`. User-guided investigation. Reads only the context you give it, states the problem back, then answers one question at a time through scouts, so the reading stays out of your context. Asked whether anything is left, it reports what is still open and where the settled decisions contradict each other or a found fact. When it ends, it writes the settled decisions to `decisions.md` and the facts behind them to `findings.md` in the change's scratch folder.
- `mahou:shape`. Settles the open decisions in a problem definition by working a design tree in rounds of questions until every branch is settled. Behavior and decisions only, never implementation.
- `mahou:design`. Designs the system for a settled definition, one area at a time as a design tree (data model, schema, data flow, rules, lifecycle, scheduled process, component architecture, contract, UI, extensible; a UI branch asks which states the element reaches, such as loading, empty, error, disabled and success), then hands the tree to `write-documentation`. The ending first reads every note in the docs folder through a docs-scout, so the list of touched notes covers the whole folder rather than only what the session opened, and says which notes were read and found untouched. Above endpoints, functions and files.
- `mahou:program-design`. Turns a settled design, or a change proposed in the conversation, into a program design, one repository at a time. Reads the code and the conventions, then proposes each branch (a package, a screen or an entry point) part by part, and you correct each part before the next opens. A root is a repository, or a host app and the library it builds a surface from. A screen's layout is worked out on a prototype, opened or created and iterated with you until it shows the final screen, and lists every state the screen shows the change in with the component that renders it, the route's pending and error components included. The prototype settles how the screen looks and behaves, never how it is coded, and the component tree names each component's source, the component a wiki entry defines for that screen or an app component, proposed from the wiki's frontend entries first so a screen an entry covers never becomes custom code. Every part follows the conventions even where the code around it does not, and before a part is shown a `program-design-reviewer` checks it against the root's conventions; the part's message says what that review changed and which findings were left out. Every part is a representation, never code: package layout, screen layout, component tree, derivation ledger, callstack, control flow, interfaces as JSON Schema, class diagram, module list, closed by a list of the conventions each part follows, which always includes the wiki's design red flags and settles without your confirmation. A part that changes something that exists shows what the change adds, alters and removes: a callstack marks its lines in a `+`/`-` column, a derivation ledger marks its lines `+`, `-` or `~` and each group `new`, `touched` or `unchanged`, a module list marks a file another branch defines as shared, and control flows and class diagrams are drawn as diffs. Code is cited as `[[path#symbol]]`, the one reference form every skill uses. The derivation ledger tags each value from a fixed set (what the part receives, configuration, shared state, values read from outside, values the part holds, functions, computed values). The one skill that proposes instead of asking, because the design already made the decisions. Records each root in the change's scratch folder and reconciles departures with the design notes at the end.
- `mahou:spike`. Answers a design question by building the smallest working version of the real thing and running it against reality. Throwaway code that never merges; the answered question and the findings are the product, and both live in the change's scratch folder. A question about states (a lifecycle, retries, concurrent actors) can be answered by model checking: the rules you agreed to become invariants of a TLA+ model, TLC finds the shortest path to each broken rule, and you decide whether the system or the rule is wrong.
- `mahou:test-design`. Turns a settled design into the test cases and manual validations that prove it, before any code exists, with the Classification Tree Method: one tree per repository, entry points or flows as roots, classifications, partitions, then a combination matrix whose rows are marked test, manual or both, with a ★ marking the rows the change adds and unstarred rows the cases the existing suite already covers. `Deleted:` lines list suite tests the change removes. On a frontend, every state a screen reaches gets at least one row. When a program design exists, the rules its parts require and the results they guarantee become classifications too, and one no design leaf covers is shown to you as a gap. You settle every level. The settled trees and matrices are written to the change's scratch folder for `implement` to read across sessions.
- `mahou:implement`. Gets a designed and test-designed change written by one subagent per repository, each briefed with the tasks, the design notes, its matrix rows with their ★ marks and any `Deleted:` lines, the repository rules and the report shape. The repository rules tell it to use the component or library a wiki entry defines instead of writing a custom equivalent, starting frontend screens from the wiki's frontend entries. The prototype and the program design bind the code only as far as `agentic-review`'s bounds say, so the subagent writes the code the conventions ask for and reports each place the code departs from the program design. Records results and flags in `implementation-status.md` in the change's scratch folder instead of relaying them as they land, each decision with enough context to decide without asking back; only a question a subagent cannot continue without reaches you at once, repeated at the top of every reply until you answer it. It has each subagent commit through `commit-changes`, then runs `validate` one repository at a time, where the subagent fixes and commits every failing row whose fix only makes the code do what previous decisions settled; a row it cannot fix that way comes to you as a blocking question, your decision is applied and the rows re-run until every one passes, and a bug outside the rows becomes an open item. Once every repository is validated it runs `agentic-review` on all of them, once, has the subagent commit the review's fixes, and records each finding the review skipped as an open item for you to apply or leave, with the problem the reviewer saw, why it proposed the change and why the review skipped it. Fixes made after the review get no further review round. Then `consistency-checker` per repository before it reconciles the docs and the scratch-folder records that drifted. The final report comes from `implementation-status-report`, which also groups departures from the program design, type escape hatches and repeated workarounds of the same shape as a sign the program design is wrong at that spot, for you to decide on. Moves tasks through whatever tracker the project declares. Writes no code and pushes nothing.
- `mahou:implement-with-tdd`. Runs `implement` as written, but writes each repository's code test first: a tester subagent writes the failing tests for the ★ rows, updates the unstarred ones whose expected outcome changed and removes the deleted ones, and validates each round, an implementer subagent writes the code, and the session relays every exchange between them and records it in `implementation-status.md` instead of showing it to you. Nothing is committed until the tester approves.
- `mahou:validate`. Runs the manual rows against the running system, through a browser, over HTTP or on an Android device, with before and after state as evidence, and leaves an HTML report. Brings up everything the rows need without asking, and inserts or mutates local records to reach a row's path without approval, deleting or reverting each before the run ends. Fixes a failing row without asking when the fix only makes the code do what previous decisions settled, and lists each fix in its report, and leaves it uncommitted unless the caller says otherwise; a failure whose fix would change a previous decision comes back as a decision, and a bug no previous decision covers is reported and not fixed. After two failed fixes on the same row it tests the assumption both fixes shared, and blocks the row with the evidence when the assumption is wrong. Runs the health check from `.mahou/validate.md` before the first row and after a failure.
- `mahou:validate-setup`. Typed. Learns from the repository how the system launches, is driven, observed and isolated, writes `.mahou/validate.md` (Launch, Doctor, Drive, Evidence, Cleanup) and one file per feature, and proves it by driving one feature end to end. Its upkeep mode sorts each drift into doc drift, harness gap or product regression, and reports regressions without fixing them.
- `mahou:code-blast-radius`. Traces what an already-written change reaches, one tracer per changed element, and reports only where behavior changes for someone. Names the one fact the change is safe because of and proves it, and each finding, as far as it can: from "said so" to a script run against the real code or a reproduction in the app, marking the claims that stop short as unproven. Ends with the cheapest test to run before merging.
- `mahou:agentic-review`. Typed, or invoked by `implement`. Runs four facet reviewers (reuse, simplification, efficiency, altitude), a test reviewer when the change touches tests, and one conventions reviewer per wiki entry and project rule file on each repository, the wiki's design red flags always among them, fixes what they find without changing how the change looks or behaves, the contracts that cross a deployable's boundary, which deployable and layer does each job, or the cases the tests check; names, file locations, how the code splits into functions, components and hooks, the interfaces between them and test names may change even when the program design, the prototype or a decision of yours set them, and design reconciliation updates the design files afterwards; editing or adding files outside the changeset when that reduces complexity or duplication, up to three rounds, each with fresh reviewers given a ledger in the change's scratch folder of every earlier fix and skip, which they treat as settled so a later round cannot undo an earlier fix; each round's status is shown and the next starts without waiting, and checks every comment the change adds against the project's comments rule. Each skipped finding is reported with the problem the reviewer saw, why it proposed the change and why the review skipped it. It edits without asking, like `validate`'s fixes, and leaves everything uncommitted.
- `mahou:human-review`. Typed only. Collects your annotations on the change, verifies each against the code, and settles every finding with you before anything is edited, then commits the approved fixes through `commit-changes` without asking again: your approval of a fix is the consent to commit it.
- `mahou:address-pr-review`. Works the review left on an open pull request: fetches the live threads, review bodies and PR comments, verifies each finding against the code (Intended only when a ruling settled what the code does, never because the prototype or a representation writes it that way), settles them with you, applies what you approve, then commits, pushes and resolves the threads. Never posts to the PR. Typed, or run by `land` when a review arrives.
- `mahou:write-documentation`. Writes or updates a note in the project's `docs/`, following the project's own charter and templates. An overview first, then the sections from the project's template that the subject needs, reasoning in callouts beside the mechanism, present tense, a diagram whenever the subject has a shape.
- `mahou:commit-changes`. Conventional commits, grouped by logical change, grouping confirmed with you before anything is committed. Never pushes.
- `mahou:release-check`. Says what breaks when the repositories of a change are released in a given order, and gives the order that breaks nothing. Finds the service boundaries from the diff and from you, including services the change does not touch and the consumers of a package the change modifies, dispatches one `compat-checker` per boundary and `code-blast-radius` alongside, and reports the findings and the release order. Changes nothing.
- `mahou:land`. Takes a written, reviewed change from its branches to merged pull requests, in the order that keeps production safe. Runs `release-check`, opens every pull request, watches them in parallel with one `babysit-pr.sh` loop each (`address-pr-review` on a review or a reviewer's PR comment, `rebase` when behind or in conflict, stop on a failed check or after three failed polls, record on merge), then walks the confirmed order, watching each merge's CI run and stopping for your production confirmation before the next. Never merges a pull request; the release follows each project's own process. Proposes skipping `release-check` for a one-repository change that crosses no service boundary, and cleans up the merged local branches at the end.

Entry points and tooling:

- `mahou:guide`. Takes your goal in plain words and activates the matching skill.
- `mahou:init`. Typed only. Seeds a `docs/` folder the project then owns: a charter, one folder per kind of note with its index, a note template, and a `## Docs` block in `AGENTS.md`. Never overwrites; re-run it to add a folder.
- `mahou:wiki`. Distilled knowledge about technologies, tools, and their gotchas, indexed for progressive discovery.
- `mahou:learn`. Typed only. The author's tool. Collects the points where a session generated friction, takes your ask directly, or both, and proposes new or iterated skills, agents, wiki entries and local files.

Asked for by name:

- `mahou:implementation-status-report`. Reports where an `implement` or `implement-with-tdd` run stands, from `implementation-status.md`: blocking questions first, shared items once, then a section for each repository that changed since the previous report in the conversation, with its status, the highlights since then and every open item with the context to settle it, and one line for the repositories that did not change. Writes nothing and touches no subagent. Asked for mid-run, or loaded by `implement` for the final report.
- `mahou:create-pull-request`. Opens a pull request from one branch, detecting its base from commit distance and writing the title and body from every commit on the branch. Waits for your confirmation before creating anything.
- `mahou:rebase`. Brings a branch up to date with its base, resolves, verifies against the suite, and reports what moved. Never pushes.
- `mahou:canvas`. Draws on a tldraw canvas served by a local app, with low-fidelity screen mockups, storage cylinders, arrows and free-text notes, in steps you can follow. You edit the same canvas live; a sticky note is a message to the agent, "Send to Agent" (or Ctrl+,) says a batch of edits is ready, and holding the mic button (or Ctrl+.) sends a voice message along with the shapes you have selected. A `mermaid` shape holds a finished diagram drawn in the canvas's style, its source validated with `superpowers:mermaid`, and mockups redraw in place when their files change. A `code-snippet` mock shows a change to a file with diff marks, notes beside its lines and a unified or side-by-side view, or shows a file as it is in its code view, and a mockup can take clicks that switch what it shows. Each cohesive element is one tldraw group, and a dotted area boxes only the parts of one thing. An area can sit inside another; it grows the outer area and moves only what sits under it inside that area. Drawing helpers create diagram boxes, arrows that stay attached to the shapes they join, and mermaid shapes sized to their diagram, mock shapes fitted to their content, and a whole test branch as a classification tree in one call, place a new shape inside a nested area by name, and move or stack shapes so the areas around them fit again. The canvas spreads across columns rather than growing downwards: related parts share a column and an unrelated part starts a new one to the right. A voice message cut short by its notification is read whole from the watch output. Every canvas has a title, the feature's name with the work in parentheses, shown as the browser tab's title. Unslops the canvas texts and exports an SVG. Mermaid stays the choice for diagrams that live as text in a note.
- `mahou:one-page-design`. Draws a settled design as one page on a `canvas`, as a journey (what the user sees step by step, what gets stored on the way and how it is read back) or an anatomy (what one thing is made of and where each part comes from). One element largest in the centre, small supporting views, and a legend for the arrows. The type comes from the context, or from you when more than one fits, and a catalogue of visual patterns backs both types.
- `mahou:architecture-exploration`. Draws a system's architecture on a `canvas` and explores ways to change it with you. It lays the options out as a grid of small drawings, one per combination, and draws a part they share step by step. After each decision it redraws the chosen one whole, beside the earlier ones, until one architecture remains. Loaded by `explore` when a question is about an architecture.
- `mahou:explore-with-canvas`, `mahou:shape-with-canvas`, `mahou:design-with-canvas`, `mahou:program-design-with-canvas`, `mahou:test-design-with-canvas`. Run the skill they name on a `canvas` instead of in the chat. Explore lays the answers out freely next to a decision log. Shape and design draw the tree as one area per branch, leaves on the left and prose and representations on the right, with questions as violet cards and two kept open at a time; shape closes with a breadboard of the settled tree, the places a person moves through, their pieces and the actions between them, with the gaps it finds settled back into the tree, when the tree defines such places; design turns a settled branch's diagrams into `mermaid` shapes and records in the chat at the end. Program design draws each part of a branch in its own area, a screen's layout as one mock per state copied from the prototype, its component tree and derivation ledger from bundled mockups with arrows showing where each value goes, a file's contents as a code-snippet in its code view, and a service's parts as mermaid diagrams (package layout, callstack, standards), interface cards (interfaces) and a file tree (module list), one column per branch, every card, line and file marked as added, changed, removed or unchanged with a closing legend, while the record file keeps the text form. Test design draws the candidate roots on a map of the system for you to pick, then every branch of a tree at once as a classification tree marked proposed until you approve it with its matrix under it, a dot under each partition that a row picks and a ★ column marking new tests, each branch drawn from a spec kept as data in a script.
- `mahou:fast-track`. Runs a canvas stage skill (shape, design, program design, test design) with the whole tree laid out at once. Decisions that files in the scratch folder already show become ✓ leaves without a confirmation round, a decision that follows from settled leaves or from the code settles without being asked, every open question is asked in one round, and a branch settles when its last question closes. Anything outside the scratch folder still waits for you. Typed once for the session, or loaded by a stage skill whose arguments ask for a fast track.
- `mahou:telepathy`. A mode: the conversation moves out of the chat and into markdown files in the change's scratch folder, served as a page you edit in the browser. Click a block to edit it or `+` to write under it; Enter or clicking away sends, and each edit reaches the agent's pane through herdr as a message, which the agent answers by writing in the files. The server tracks who wrote each block in `.meta.json`, picks up the agent's writes by diffing against its last snapshot, and merges your edit with the agent's when both touched the same block, opening a merge editor only when the same lines changed. Requires herdr and Bun.

Loaded by other skills, never typed:

- `mahou:basics`. Philosophy, rules, the scratch convention and its `status.md` tracker, the local layer, updating a scratch-folder record in the same turn the work changes what it records, and starting every subagent from the folder the session started in.
- `mahou:docs`. How to find the project's docs folder, what its structure is made of, and the rule that the charter wins. Loaded by `write-documentation`, `explore`, `design`, `init` and the two docs agents.
- `mahou:design-tree`. The tree format, the frontier, the question and answer rules, and how questions and branches merge.
- `mahou:changeset`. Which repositories, which base (found by commit distance with a bundled script), which diff, and the rule separating what a change introduced from what predates it.
- `mahou:lookup`. Where a fact comes from: the routing between the scouts and the researcher, the rule for facts outside the project, and how a verified fact is told apart from an asserted one. Loaded by `explore` and `design-tree`.
- `mahou:prototype`. Shows a screen element as an interactive HTML prototype and iterates it with you, round by round, each round opened in Plannotator so you annotate the rendered page, after checking which states the element can reach and naming those nobody asked for, following the patterns the wiki's frontend entries and the project's rule files set. Loaded by `explore` when a question is about what something looks like, and by `design` for a UI branch.

## Agents

Dispatched by skills, never called directly. Every one writes findings and edits nothing.

- `reuse-reviewer`, `simplification-reviewer`, `efficiency-reviewer`, `altitude-reviewer`, `conventions-reviewer`: one angle each, dispatched fresh by `agentic-review` every round, with the ledger of earlier rounds from the second on. The reuse reviewer also checks the wiki entries that match the change, since a wiki entry may define the component or library the change builds by hand. Each conventions reviewer reads the one wiki entry or project rule file it is given and cites it.
- `test-reviewer`: the tests a change adds or changes, dispatched by `agentic-review` when the diff touches tests. In a worktree of its own it breaks the behaviour each test claims, which must fail the test, and restructures only the internals, which must pass it, running each test alone.
- `usage-tracer`: one changed element, every repository in scope, dispatched by `code-blast-radius`. Reads past grep: the installed library's source, timing and teardown, stored data and feature flags.
- `code-scout`, `docs-scout`: one question against one repository or the project's docs folder, dispatched through `mahou:lookup` by `explore` and `design-tree`.
- `researcher`: one question about a library, tool or platform outside the project, answered with facts and sources and no recommendation, dispatched through `mahou:lookup`.
- `compat-checker`: one service boundary, testing the new side against the deployed other side in both directions, dispatched by `release-check`.
- `program-design-reviewer`: one proposed part of a program design against the wiki entries and project rule files of its root, before you see the part, dispatched by `program-design` once per part.
- `documentation-reviewer`: one draft against the project's charter and template, dispatched by `write-documentation`.
- `consistency-checker`: one repository after a change lands, for leftovers and for code that disagrees with the docs or with itself, dispatched by `implement` during design reconciliation.

## The project's docs

Mahou has no shared knowledge base about your project. It assumes the project keeps one itself, in a `docs/` folder with a `README.md` charter that says what each folder holds and how a note is written, and one `README.md` per folder as its index. `init` seeds that shape; `write-documentation`, `explore` and `design` read whatever is there, through `mahou:docs`. The plugin owns the process, the project owns the structure: no skill carries a template body, and where the project's charter differs from anything a skill sketches, the charter wins.

## Wiki

The wiki holds knowledge, not process: facts about technologies and tools, their gotchas, their patterns. It is organized as one index per folder, each index listing only its own level, so entries load on demand. Entries carry a `verified` date, and stale knowledge gets re-verified before it is relied on. The conventions reviewer treats it as the standard a change is measured against.

## Global and local

The plugin is the global store: skills live in `skills/`, wiki entries in `skills/wiki/references/`. A project can add its own layer in a `.mahou/` folder at its root:

- `.mahou/basics.md` for project-level standing rules, and for naming the docs folder when it is not `docs/`.
- `.mahou/<skill>.md` to change how a skill behaves in this project.
- `.mahou/wiki/` for local wiki entries, with the same index-per-level shape.

Local wins over global when the two conflict, and whether `.mahou/` is committed is each project's call.

Separately, `.scratch/<change-slug>/` at the project's root holds the artifacts a skill produces for you and keeps between rounds: design handoffs, prototypes, drafts. It is meant to be gitignored; throwaways still go to `/tmp`.

## Dependencies

- `superpowers:unslop` and `superpowers:mermaid`, from the `superpowers` plugin in this marketplace, for the writing pass and diagrams in `design` and `write-documentation`. Without them those skills say so and continue unvalidated.
- The `plannotator` CLI for `human-review` and `prototype`.
- Node and npm, plus the `agent-browser` CLI, for `canvas`. The app installs into `~/.cache/mahou-canvas` on first run.
- herdr and Bun for `telepathy`. Its server's dependencies install next to the script on first run.

## Growing the toolbox

`mahou:learn` reads a conversation for the points where the user had to steer it (a format change, a request outside the running flow, a correction of something the agent produced) and proposes, ordered by confidence then impact: new skills, iterations on existing ones, agents, wiki entries, and local files. The skills above were brought in from real sessions rather than designed upfront, and the same loop grows them further.

## Installation

As a local marketplace:

```bash
/plugin marketplace add local ~/workspace/asermax/claude-plugins
/plugin install mahou
```

Or directly:

```bash
/plugin install ~/workspace/asermax/claude-plugins/mahou
```
